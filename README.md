# 校递达 · 校园跑腿小程序

浙江中医药大学的校园快递代取 / 代带餐食互助平台。
**一个小程序，进去选身份**（用户 / 骑手）+ **uniCloud 后端（支付宝云）**，资金走「预付托管」。

```
用户下单付款 ──▶ 平台托管 ──▶ 骑手接单 ──▶ 送达 ──▶ 结算（平台服务费 8%）
```

> 体验入口与账号见 [测试目录.md](测试目录.md)；部署见 [docs/usage.md](docs/usage.md)。

## 2026-11-14 · v1.11.3（1 元起提 + 大图加载提速）

- **提现门槛 3 元 → 1 元**：学生单笔收入常常只有几块，3 元门槛等于提不出来。
  风控不变（单笔 ≤200 元、每天 ≤5 次、单日 ≤500 元、两次间隔 10 分钟）。
  云端 `xyyx-settings` 里如果管理员改过配置，靠 `settings_version` 一次性迁移把
  `minWithdrawYuan` 同步成 1，其它配置不动。
- **大图加载提速**（原来 5 片串行要 3~5 秒）：
  - 服务端分片 160KB → **400KB**，大多数图一次往返就拿完；
  - 客户端剩余分片**并发取**（并发 4），大图压到 1~2 次往返；
  - 预览页预取左右两张，滑过去基本秒开；
  - 已解出的图有内存缓存，反复看不用重新取。
- 实测口径：400KB 图（base64 546KB）= 2 片，1 次串行 + 1 次并发 ≈ 一次往返的体感。

## 2026-11-14 · v1.11.0（图片换方案：字节直存数据库；提现全链路闭环）

### 图片：不再依赖云存储读取 / CDN 域名 / 本地文件系统

真机上「看图黑屏」已经修了三轮（分片、落盘、预览页），链路里任何一环在真机上出问题都难定位。
这一版直接**换掉整条链路**：

- 上传时（`uploadImageBase64`）顺手把压缩后的图 `base64` 存进新集合 **`xyyx-images`**
  （`_id = i_ + md5(fileID)`，≤620KB 才存，超过仍走云存储兜底）。
- `getImageData(fileID, offset)` 优先返回数据库里的切片（`source:'db'`，按 4 字符对齐切，客户端直接拼）；
  老图没有直存记录时读云存储，**读成功就自动补存**，下次直接命中，无需迁移脚本。
- 客户端新增 `resolveImageSrc()`：三条完全独立的路径依次兜底，并把每条失败原因带回页面
  - `data`（云函数分片 → data URI 直接交给 `<image>`，不落盘、不看域名）
  - `file`（同样的字节写本地临时文件，data URI 超过 900KB 时用）
  - `url`（云存储临时链接，最后兜底）
- 预览页底部会显示走了哪条路（`原图 · 直读` / `原图 · 本地文件` / `原图 · 临时链接`）；
  三条都失败才显示具体原因（`直读:…；落盘:…；链接:…`），可点「重试」。
- 聊天页老消息、订单详情页图片都改走 `resolveImageSrc`；聊天图片上传压到 1280 宽 / quality 65，
  绝大多数落在 620KB 以内，直接命中数据库直存。
- `xyyx-cron` 每天清理 120 天前的直存图片（`cleanImageData`）。

### 提现：状态可追踪、失败自动退回、后台可核查可重发

- 新增集合 **`xyyx-withdrawals`**：每笔提现一条（`_id = out_bill_no`），记录微信转账状态
  （`pending / WAIT_USER_CONFIRM / TRANSFERING / SUCCESS / FAIL / CANCELLED / EXPIRED`）。
- `requestWithdraw` 走 `issueTransfer()`：登记提现单 → 调微信 `transfer-bills` → 落状态。
- **失败只退一次**：冲正用 CAS（`rolled_back` 只能 false→true），微信回调 / 用户轮询 / 定时任务
  三条路同时来也不会重复加钱。
- 新增 `xyyx-pay.myWithdrawals()`（钱包页「最近提现」显示状态）、`queryWithdraw` 返回 `package_info`
  以支持「去确认」（待确认收款时重新拉起 `wx.requestMerchantTransfer`）。
- `xyyx-pay.syncWithdrawals()` 由 `xyyx-cron` 每轮调用：确认页超时/客户端崩了也能把余额退回。
- 后台「提现记录」升级：状态徽章、失败原因、在途/成功/失败统计、**一键同步在途状态**、
  失败单 **一键重发**（`xyyx-admin.reissueWithdraw` → `xyyx-pay.reissueWithdraw`）。
- 注：`reissueWithdraw` 需要用户余额足以重新扣款；微信「用户确认」模式下重发后仍需骑手在小程序里确认收款。

## 2026-11-13 夜 · v1.10.2（修「小图能看、大图全黑」）

- 根因：`appendFileSync(path, base64, 'base64')` 在微信里对 base64 解码不可靠，多片拼接出来的文件是坏的
  —— 单片（小图）用 `writeFileSync` 没问题，多片（大图）就黑屏 + 「原图显示失败」。
- 改为：分片取回后拼 base64、最后 `writeFileSync` 一次写入，并 `statSync` 校验文件大小；
  写失败再退一步 `base64ToArrayBuffer` 写。
- 预览页失败时会显示具体原因（而不是只有一句「原图加载失败」），点提示可重试。
- 图片引用同时支持 `cloud://` 和 `https://`（不同服务空间返回格式不同）。
- 版本号 1.10.2。

## 2026-11-13 晚 · v1.9.11（大图分片落盘 + 输入框真对齐）

- **大图仍然看不了**：上一版虽然分片取图，但在客户端先把所有分片拼成一个巨大的 base64 字符串，
  再一次性 `writeFile` —— 接近 1MB 的图在小程序里很容易卡死/写失败。
  现在改成**边取边 `appendFileSync(..., 'base64')`**，不拼大字符串、不占大内存；分片长度由服务端
  保证是 3 的倍数，逐片解码不会有填充问题。
- **拿不到原图时也能看出原因**：预览页底部会显示「原图加载失败，点此重试」；点一下重新取，
  同时会回退试一下云存储临时链接（如果域名白名单配过也能用）。
- **输入框真正对齐**：微信 `textarea` 是原生组件，直接把 `height/flex` 加在它身上经常不生效。
  现在是「普通 view 外层 + textarea 内层」：外层 84rpx 和「＋」「发送」同高，内层随内容长高。

## 2026-11-13 图片修复（头像 / 聊天图片 / 订单图片）· v1.9.6

> 版本号：`1.9.6`（versionCode 196），已出正式包并上传微信后台开发版本；
> 真机预览码：`docs/code-image-fix-20261113.jpg`。

- **头像存不进去**：客户端已经把头像压成 data URI，但云对象 `updateProfile` 还留着
  `max: 300` 的旧校验，几 KB 的 data URI 直接被判「头像过长」→ 头像永远保存失败。
  现在放宽到 16KB 并校验格式（`data:image/…` / `/static/…` / http），客户端压到
  240px，超了自动降档再压。
- **聊天图片显示不出来**：之前只存 `cloud://` fileID，展示要靠 `getTempFileURL`
  的临时链接 —— 小程序 `<image>` 走的是 downloadFile 域名白名单，云存储 CDN 域名
  没配就整片裂图；临时链接还会过期，旧消息过一阵子同样打不开。
  现在发图片时同时生成一张**缩略图 data URI** 跟消息一起存，气泡直接画它：
  不发额外请求、不看域名、不会过期。原图仍然传云存储，点开预览时优先用原图，
  取不到就退回缩略图。
- **订单图片 / 取件送达留痕**：同一套问题，发布订单和拍照留痕时也带上缩略图
  （`image_thumbs` / `pick_proof_thumb` / `deliver_proof_thumb`）。
  为了不把返回体撑爆：**只有详情接口下发缩略图，列表接口不带**。
- **老数据兼容**：没有缩略图的历史消息/订单继续走临时链接，链接拿不到时显示灰底
  而不是裂图图标；`cloud://` 头像退回默认头像。
- **回归测试**：新增 `tests/image-flow.spec.js`（30 项断言：头像上限、缩略图落库、
  详情/列表的字段边界、聊天图片、留痕缩略图）。

## 一个 App，两种身份怎么隔离

| 层 | 做法 |
| --- | --- |
| 接口 | 用户端只能调 `xyyx-user`，骑手端只能调 `xyyx-rider`，方法集不重叠 |
| 字段 | 服务端 `taskForUser()` / `taskForRider()` 两套白名单 |
| 数据 | 所有集合 `permission: false`，客户端无法直连数据库 |
| 聊天 | 只有该订单的发布者和骑手是成员，服务端 `assertChatMember` 兜底 |

**骑手接单前拿不到任何手机号**；接单后能看到完整号码（要打电话），
用户永远拿不到骑手的真名、学号、学校。

## 安全

- 密码 `scrypt` + 每用户随机盐 + pepper（不用明文、不用裸哈希）
- 写接口带 nonce 防重放，按 uid 限流，参数白名单
- 记账有 `idempotency_key` 唯一索引，重复回调不重复入账
- 聊天消息纯文本入库，仅订单双方可读，限流 30 条/分钟
- 仓库零密钥：提交前跑 `node tools/scripts/check-secrets.mjs`

详见 **[docs/security.md](docs/security.md)**。
