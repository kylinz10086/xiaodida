## C. 只有你能拍板的产品决策

### C1. 钱怎么走？（这个不定，后面全白做）

现在代码里 `completeTask` 给跑腿员加收入，但发布者不扣钱 —— 没有支付、没有余额、没有提现。
`微信支付信息.txt` 里有商户号（1111597518）和 API 密钥，说明本来打算接微信支付。

三条路，选一条：

| 方案 | 说明 | 工作量 |
| --- | --- | --- |
| ① 纯撮合（不碰钱） | 平台只展示需求，线下自己转账（微信/支付宝）。手续费 0，合规风险最低 | 最小，改文案即可 |
| ② 预付托管 | 发布时微信支付冻结，确认完成后结算给跑腿员，平台抽佣 | 大：要接微信支付 v3 + 分账/提现 + 退款 |
| ③ 余额充值 | 先充值到平台余额，下单扣余额 | 中：要接充值 + 提现审核 |

我的建议：**先做 ①**把产品跑通（现在 `miniprogram/` 就是这样），
验证有人用之后再上 ②。

### C2. 学校范围

代码里写死「浙江中医药大学」。要不要支持多学校？（涉及数据隔离、审核、运营）

### C3. 审核合规

微信对「跑腿/代取」类目审核较严，通常需要：
- 类目选「生活服务 > 跑腿代购」或「教育 > 校园服务」
- 要有用户协议和隐私政策页面（现在没有）
- 涉及位置的要在 `app.json` 声明 `scope.userLocation`（已声明）

## D. 之后的开发顺序（我按这个推）
