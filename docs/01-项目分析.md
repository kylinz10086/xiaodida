# 01 · 原项目分析

> 写于 2026-11-10 晚。目的是让明天的你（或者接手的人）五分钟内明白这套东西是什么、卡在哪。

## 一、仓库里有什么

`F:\xiaodida` 下是三套**独立**的 uni-app 工程，加一份支付凭据：

```
xiaodida/
├── 校递达app客户端/      ← 主工程：学生端小程序（Vue2 + uView + uniCloud）
├── 校递达app后端管理/    ← 管理后台（uni-admin 模板改的）
├── 微信登录/             ← uni-id-pages 登录模板，学习/参考用
├── 微信支付信息.txt      ← ⚠️ 含商户号与 API 密钥，绝对不能进公开仓库
└── miniprogram/          ← 今晚新做的原生小程序（可离线跑）
```

### 1. 校递达app客户端（主工程）

- **框架**：uni-app + Vue 2 + Vuex + uView 1.x（`easycom` 规则 `^u-(.*)`）
- **后端**：uniCloud 阿里云，`_spaceID = mp-48da081d-d25c-4a57-980e-bb8dfc3f52a9`
- **小程序 appid**：`wxab71ca588522f56d`
- **业务**：校园跑腿 —— 发布「代取快递 / 代带餐食 / 其他」需求，别人接单完成

页面结构（`pages/xyyx/`）：

| 页面 | 作用 |
| --- | --- |
| `index/index` | 首页：搜索、发布入口、任务市场列表（按时间/价格排序） |
| `release-requirements/` | 发布需求表单（类型、标题、描述、物品信息、起终点、时间、金额、联系方式、图片、备注） |
| `requirement-detail-info/` | 任务详情 |
| `order/order` | 我的订单（全部 / 我发布的 / 我接的单 × 状态筛选） |
| `userinfo/userinfo` | 我的：资料、统计 |
| `search/search` | 搜索 |
| `notification/` | 通知设置 |
| `route-detail/` | 路线与导航（模板遗留的公交/驾车/骑行/步行页） |
| `pages/oyyl-index/` | 原模板首页（`oyyl-index`、`test`、`login`），基本没用上 |

数据层已经重构过一轮，方向是对的：
**所有读写都走单一云对象 `xyyx`**，`store/index.js` 里 `getXyyx()` 一行拿到实例，
Vuex action 统一 `{code, msg, data}` 判错。这比把业务逻辑散在页面里好太多。

云对象 `xyyx` 的接口（`uniCloud-aliyun/cloudfunctions/xyyx/index.obj.js`）：

```
getTaskList   getTaskDetail  publishTask  acceptTask  completeTask
confirmTask   cancelTask     abandonTask  getMyTasks  getUserInfo  updateUserInfo
```

数据表：`xyyx-tasks`、`xyyx-users`（schema 已写好在 `uniCloud-aliyun/database/`）。

### 2. 校递达app后端管理

uni-admin 模板 + 若干 uni_modules（图表、表格、上传等）。目前**没有任何自定义业务页面**，
就是模板本身，`pages/` 下全是 `demo` / `system` / `uni-stat`。要真用起来得自己加
「任务管理 / 用户管理 / 提现审核」页面。

### 3. 微信登录

`uni-id-pages` 的一整套登录/注册/绑定手机号页面，带 `doc/` 里的三份教程 docx。
它的价值是：主工程 `pages.json` 里也注册了 `uni_modules/uni-id-pages/pages/**`，
登录态（`uniIdToken`）就是靠它拿到的。**主工程的登录依赖这套模块，别删。**

## 二、任务状态机（两套前端共用）

```
            接单                   完成 / 发布者确认
[1 待接单] ────→ [2 进行中] ────→ [3 已完成]
     │                  │
  取消│              放弃│（回到市场，重新待接单）
     ↓                  ↓
[4 已取消]          [1 待接单]
```

| 操作 | 谁能做 | 前置状态 | 结果 |
| --- | --- | --- | --- |
| publishTask | 发布者 | — | 1 |
| acceptTask | 非发布者 | 1 | 2 |
| completeTask | 接单者 | 2 | 3，给接单者加 `total_income` |
| confirmTask | 发布者 | 2 | 3 |
| cancelTask | 发布者 | 1 | 4 |
| abandonTask | 接单者 | 2 | 回 1 |

## 三、发现的问题（今晚已修的标 ✅，没修的标 ⏳）

### 已修

| # | 问题 | 修法 |
| --- | --- | --- |
| ✅1 | `pages.json` 全局 `navigationBarTitleText` 是 **"uView"**，所有页面标题会显示成 uView | 改成「校递达」 |
| ✅2 | `manifest.json` 的 `description` 是「多平台快速开发的UI框架」，H5 标题是「uView UI」 | 改成校递达文案 |
| ✅3 | `package.json` 的 repo / bugs / homepage 全指向 **uView 上游仓库**，别人一看以为这项目是 uView | 指向本仓库，补 uni-app/uniCloud 关键词 |
| ✅4 | 云对象 `xyyx-task`、`xyyx-user` 与 `xyyx` **重复**，且字段要求不一致（`xyyx-task` 要求 `thing`，`xyyx` 用 `title`）。一旦误部署就是两套逻辑打架 | 各加一份 `README.md` 标明「已废弃，别部署」 |
| ✅5 | 没有 git 仓库，没有任何版本记录 | `git init` + 上传 GitHub |
| ✅6 | 没有 `.gitignore`，`unpackage/`、`node_modules/`、私有配置会一起入库 | 已加 |

### 还没修（按优先级）

| # | 问题 | 说明 |
| --- | --- | --- |
| ⏳1 | **没有资金闭环** | `completeTask` 直接给接单者 `total_income += money`，但发布者那边**不扣钱**，也没有余额表、没有提现。现在这套「收入」是会计幻觉，上线前必须补：订单支付 → 平台托管 → 确认后结算。`微信支付信息.txt` 里的商户号说明原本是想做微信支付的，但代码里一行支付都没接 |
| ⏳2 | 没有评价 / 举报 / 申诉 | 跑腿类产品最容易被刷单和放鸽子，至少要有完成后的互评和拉黑 |
| ⏳3 | 没有实时位置与通知 | 接单后双方只能靠手机号/微信联系，没有站内消息；`notification` 页只是设置项，没有推送通道 |
| ⏳4 | `getMyTasks` 的 `dbCmd.or` 用法 | 现在写的是 `.where(dbCmd.or({...},{...}))`，阿里云 uniCloud 支持这种顶层逻辑操作符，但和 `status` 组合时用 `dbCmd.and` 包了一层，参数一多容易出错。建议改成显式两次查询合并，或改用 JQL 视图 |
| ⏳5 | 模板遗留页面 | `pages/oyyl-index/*`、`route-detail/navigation_*` 与快递业务无关，页面越堆越多会拖慢构建、也让审核看不懂 |
| ⏳6 | 后端管理没业务页面 | 见上文 |
| ⏳7 | 没有测试 | 云对象全是纯函数式逻辑，其实很容易写单元测试；现在零覆盖 |

## 四、一句话结论

> 业务骨架（数据表 + 云对象 + 状态机 + 三个 Tab 的页面）已经是完整可用的，
> **真正缺的不是页面，是资金闭环和云端部署**。
> 页面层面今晚新做的 `miniprogram/` 已经能把完整流程跑通，可以用来演示和继续迭代。
