## 0. 怎么用这份提示词

- **整份粘贴**：让 Agent 先读 §1-§4 建立约束，再按批次推进。适合能连续跑多轮的工具。
- **分批粘贴（推荐）**：每次只贴「§1-§4 + 一个批次」。每批改完让 Agent 提交报告、你人工验收，再做下一批。批次之间互相独立，中断不会烂尾。
- **顺序不要打乱**：批 1 会新建一个详情页组件，批 2 的评价入口要挂在这个页面上；先 2 后 1 会重复返工。

## 1. 角色

你是一名在**存量工程**上做增量的前端 + uniCloud 后端工程师。你的首要目标不是"加功能"，而是**把已经存在但没接通的东西接通**，并且**不破坏现有资金流语义**。

判断标准只有一条：**改完之后，一个第一次进小程序的用户，能不能不打电话就搞清楚"我的东西到哪了"。**

## 2. 工程事实（动手前必须确认，不要凭猜测）

| 项 | 事实 |
|---|---|
| 框架 | uni-app + **Vue 2** + Vuex；UI 库 uView 1.x（`easycom` 自动注册 `u-*`） |
| 用户端 | `apps/user`（分包页面在 `pages/xyyx/*`；**内嵌了骑手页** `pages/rider/*`） |
| 独立骑手端 | `apps/rider`（另一个小程序工程，`apps/user/pages/rider` 是它的内嵌子集） |
| 后端 | uniCloud **云对象**（`.obj.js`），不是普通云函数；公共库 `cloudfunctions/common/xyyx-common/index.js` |
| 云对象 | 用户端 `xyyx-user`、骑手端 `xyyx-rider`、支付 `xyyx-pay`、定时 `xyyx-cron`、后台 `xyyx-admin` |
| 数据表 | `xyyx-tasks` `xyyx-users` `xyyx-wallets` `xyyx-reviews` `xyyx-refunds` `xyyx-settings` `xyyx-transactions` 等 |
| 数据权限 | **所有 `xyyx-*` 表的 `permission` 都是 `read:false / create:false / update:false / delete:false`** |
| 由此得出 | **前端永远不能直连数据库**。要读任何业务数据，必须走云对象方法。新增列表 = 新增云对象方法，没有例外。 |
| 字段出口 | 任务数据只能经 `C.taskForUser(task, viewerId)` / `C.taskForRider(task, riderId)` 下发 |
| 配置 | 费率、上下限、客服电话等在 `xyyx-settings`，通过 `getProfile().settings` 下发，**前端不得硬编码任何费率/区间** |
| 金额 | 客户端收"元"，服务端立刻转"分"，**库内只存分**（字段后缀 `_cent`） |
| 状态 | 任务 `status`：1 待接单 / 2 进行中 / 3 已完成 / 4 已取消；`pay_status` 独立 |
| 风格 | 代码注释是中文、解释"为什么这么写"。**你的新增注释保持同样风格和密度。** |

## 3. 硬约束（违反任何一条 = 打回重做）

1. **不许改资金语义**。托管、抽佣、退款通道费、补差价、幂等整套逻辑一行都不许动。若某个 UI 需要金额，只读取服务端下发的字段。
2. **不许前端直读数据库**。需要新数据 → 在对应云对象加方法 → 用 `C.pick` / `C.taskForUser` 等出口裁剪字段。
3. **不许跳过字段隔离**。任何返回任务的接口都必须过 `taskForUser` / `taskForRider`。
4. **不许新增 npm / 三方依赖**（含新的 UI 库、新的图表库、新的 IM SDK）。用现有的 uView 组件 + 原生小程序 API 解决。
5. **不许重写 `components/` 下的公共组件**（`mission-list-item` `order-list-item` `htz-image-upload` 等）的行为，只能做**向后兼容的新增**。
6. **不许一次性格式化整个文件**。diff 尽量只包含你真正改的行，方便人工 review。
7. **不许动 `apps/rider`**，除非批次里明确写了。本轮所有改动都落在 `apps/user` + `cloudfunctions`。
8. **不许删旧页面**（`requirement-detail-info.vue` 等）。你可以新建页面并把入口切过去，旧页面保留但加 `// @deprecated` 注释说明被谁取代。
9. 每改一个云对象方法，**必须检查是否有 `checkNonce` / `rateLimit`** 的保护需求；写操作没有 nonce 校验的，说明理由。

### 批 2 · 评价闭环：把死数据变成看得见的信用

**要解决的问题**：`submitReview` 后端写好了、`xyyx-reviews` 表建好了、`users.rating` 也算了，但前端一个入口都没有，云对象也没有"读评价"的方法，导致评分永远 5.0。

**必读**：`.../cloudfunctions/xyyx-user/index.obj.js:474-503`、`.../database/xyyx-reviews.schema.json`、`apps/user/store/index.js`（看 action 命名习惯）。

**做**：
1. **新增云对象方法** `listReviews({ riderId, taskId, page, pageSize })`（放 `xyyx-user`，骑手收到自己的评价后续再加到 `xyyx-rider`）：
   - 支持按 `riderId`（骑手主页）或 `taskId`（订单详情）；
   - 返回 `{ score, content, create_time, from_nickname, from_avatar }`；
   - **必须裁剪**：不返回 `from_id` 明文、不返回用户手机号；
   - 分页，默认 10 条。
2. **新增云对象方法** `getRiderProfile(riderId)`：昵称、头像、`rating`、`rider_rating_count`、完成单数、加入天数。同样只走白名单字段。
3. **前端 · 评价入口**：订单 `status===3` 且 `role==='publisher'` 且未评价时，详情页底部出现「评价骑手」。点击弹层：1-5 星 + 快捷标签（准时 / 态度好 / 包装完好 / 沟通及时，可多选，**作为 content 前缀拼进去，不新增表字段**）+ 200 字文本。提交走 `submitReview`。
4. **前端 · 评价展示**：详情页骑手卡片下方展示该骑手最近 3 条评价（星星 + 一句话），点「查看全部」进骑手主页。
5. **前端 · 未评价提醒**：订单列表里"已完成但未评价"的卡片加一个小角标「待评价」，不打断流程。
   - ⚠️ 这里有个坑：现在的 `taskForUser` 没有"是否已评价"字段。**不要**在 `listMyTasks` 里对每条订单各查一次 reviews（N+1）。两个可选做法，任选其一并说明理由：
     - a) 列表页只加**静态**角标「待评价」，点进详情页再用 `listReviews({taskId})` 判断是否真没评；
     - b) 在 `listMyTasks` 里**一次性**按 `task_id in [...]` 批量查 reviews，再合并成 `reviewed` 布尔。
6. 评分展示统一为一位小数（如 `4.8`），`rating_count < 3` 时显示「新骑手」而不是一个孤零零的 5.0——**冷启动的 5.0 会误导用户**。

**验收**：
- 完成一单 → 评价 → 列表角标消失 → 详情页能看到自己刚写的评价；
- 重复提交被后端拦住（已有 `'已经评价过了'` 校验），前端也要在提交成功后立刻把按钮置灰；

### 批 4 · 发布页提效：把 14 个填写项压到 8 个

**要解决的问题**：每次发单都要重填 10 个区块、14 个填写项，价格还得自己猜。

2. **价格建议**（纯前端，不调新接口）：

   - 按「距离档 × 物品大小档 × 时段」给一个建议区间，例如 `3-5 元 / 5-8 元 / 8-12 元`；
   - 快捷价按钮由"硬编码 6 个"改成"建议区间内的 3 个档 + 自定义"，**必须保留自定义输入**；
   - 建议只做提示，不拦提交。
3. **必填收敛**：「物品类型」「预估重量」改为**选填**并折叠进「更多信息」（默认收起）；「微信号」选填并在手机号已填时隐藏。
4. **修掉类型越界（先看清语义再决定，别急着"放宽后端"）**：
   - 现状：前端 `typeList` 有 4 项「快递/带餐/**代购**/其他」（`release-requirements.vue:255`），后端只有 3 类且第 3 类叫「其他」（`common/index.js:190`），发布接口 `max:3`（`xyyx-user:119`）。

**验收**：
- 第二次发单，地址自动带出，能一键换；
- 金额区在有起终点时给出建议，无坐标时静默隐藏（不报错）；

## 8. 明确不要做的事

- 不要顺手重构 `store/index.js`。它是 V1 遗留，重构风险远大于收益。
- 不要给详情页加"炫技"的动效或地图自定义样式。**信息密度 > 视觉花活**。
- 不要把 `apps/rider` 也改一遍（双端合并是 P2-18，单独排期）。
- 不要在没被要求的情况下动 `xyyx-pay` 和 `pay-notify`。支付回调是全项目最不能出错的地方。
- 不要把"建议区间"写成"必须按此价格"——定价权是用户的，我们只给参考。
- 不要为了通过验收去删测试数据或改 mock。**没做就是没做，写进"没能验证的"。**
